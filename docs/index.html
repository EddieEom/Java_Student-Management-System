01 / THE PROJECT

무엇을 해결하려 했는가?

단순한 CRUD 구현보다, 같은 비즈니스 로직을 화면과 JSON API에서 안전하게 재사용할 수 있는 구조를 이해하고 적용하는 것이 이번 확장의 중심이었습니다.

BEFORE / 문제

HTML 화면에만 의존하는 서버

웹 브라우저에서 사용하는 Controller만 있으면 모바일·외부 프로그램은 데이터를 활용하기 어렵습니다. 검색·수정 등의 책임이 화면 처리와 뒤섞이면 확장 과정에서 코드 중복이 발생할 수 있습니다.

AFTER / 해결

하나의 Service, 두 가지 표현 방식

Thymeleaf MVC 화면은 유지하고 REST Controller만 추가했습니다. 두 Controller는 같은 Service를 공유하며, 데이터 접근·트랜잭션 처리는 Repository/JPA로 분리했습니다.

기술 선택과 데이터 흐름

MVC와 API가 Service를 공유하기 때문에 웹 화면을 수정하더라도 JSON API의 데이터 처리 로직을 중복 작성하지 않습니다.

01
검색·정렬·페이징

Spring Data JPA Query Method / PageRequest. 허용 필드만 Sort 처리하고 검색 조건은 AND로 결합.

02
트랜잭션과 수정

CourseService.update()에서 영속 Entity만 수정. 커밋 시 Dirty Checking으로 UPDATE 수행.

03
REST Validation

@Valid, @RestControllerAdvice, ResponseEntity로 201/200/204/400/404와 오류 JSON 구분.

05 / BUILD & DEBUG JOURNEY

결과보다 중요한 문제 해결 과정

포트폴리오에선 ‘만들었다’는 말만으로 역량을 판단하기 어렵습니다. 요구사항과 실제 코드 사이에 무엇이 달랐고 어떻게 해결했는지를 구체적으로 남겼습니다.

ISSUE 01 · 구조 분리

Controller가 아닌 Service를 재사용

Course REST 추가 시 비즈니스 로직을 다시 작성하지 않았습니다. 기존 CourseService 검색·수정 메서드를 연결해 MVC와 JSON 표현 계층만 나눴습니다.

ISSUE 02 · 요구사항 대조

Student PUT에 @Valid 누락

10주차 PDF와 기존 Student API 소스를 비교해 PUT의 입력 검증 누락을 발견했습니다. REST 수정에서도 400 오류와 필드별 JSON을 반환하도록 보완했습니다.

ISSUE 03 · DB 연결

${DB_USERNAME} 문자열이 그대로 전달됨

SQL Server 로그인 18456 오류는 API 로직이 아니라 IntelliJ 환경변수 치환 문제였습니다. 비밀번호를 코드에 저장하지 않고 Run Configuration으로 설정해 사용자가 해결했습니다.

ISSUE 04 · 상태코드·테스트

성공 응답과 검증 근거를 분리

POST 201, PUT 200, DELETE 204, 삭제 후 GET 404를 Postman 생명주기로 정리했습니다. 32개 HTTP 스모크 기록과 사용자 SQL Server 테스트 보고는 출처를 구분했습니다.

06 / OWNERSHIP & HONESTY

어디까지 본인이 수행했는가?

기존 실습 ZIP을 바탕으로 AI를 활용한 개인 확장 프로젝트입니다. 기여도와 코드 생성 출처를 구분하며, ‘혼자 모든 코드를 직접 작성했다’고 표현하지 않습니다.
